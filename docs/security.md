# Security Model

Netrix processes sensitive operational data (credentials, terminal output,
private keys). This document describes current protections, known gaps, and
recommended hardening steps.

## Security Architecture

Netrix runs as two local processes:

1. Tauri shell (Rust) for desktop lifecycle and IPC.
2. Backend sidecar (Rust/Axum) for API, sessions, and storage.

All traffic between frontend and backend stays on localhost.

## Current Protections

### API Authentication

- A per-session token is generated by Tauri.
- Token is passed to backend via stdin (not command line args).
- HTTP endpoints require `X-API-Token`.
- WebSocket endpoints validate token-bearing subprotocol headers
  (`netrix-token.<token>`).

### Network Exposure

- Backend binds to `127.0.0.1` only.
- CORS is restricted to exact localhost and Tauri origins.
- Tauri CSP blocks `unsafe-eval`; inline styles are still allowed for current
  UI compatibility.
- Sidecar launch is owned by Tauri Rust code; no shell commands are exposed to
  webviews. App commands and core permissions are scoped by main, detached
  terminal, and detached map window labels.

### Credential Handling

- API responses do not expose plaintext host credentials.
- Vault subsystem encrypts secrets with Argon2id + AES-256-GCM.
- Vault key material is zeroized on lock and object drop.
- Vault supports in-place master password rotation (`/vault/change-password`) with
  re-encryption of all stored secrets.
- Vault status endpoint reports operational counts (`secret_items`,
  `linked_hosts`) to support safer UX decisions.
- Repeated invalid vault unlock attempts are temporarily rate-limited in
  backend memory.

### SSH Host Key Verification

- Known-hosts store supports TOFU and mismatch detection.
- Policy is configurable via `SSH_KNOWN_HOSTS_POLICY`.
- Default policy is `strict` unless explicitly overridden.

### SFTP Capability and Directory Listing

- SFTP is treated as an optional SSH capability, not as a required part of SSH
  terminal access.
- Opening a terminal never triggers SFTP probing or directory listing.
- SFTP operations use a separate SSH connection and request only the `sftp`
  subsystem, so SFTP failure does not close or interrupt terminal sessions.
- Directory listing and file preview/download are read-only. Upload streams to an
  exclusive temporary file, checks CLOSE and commits by rename. Explicitly confirmed
  replacement requires atomic-rename support. Delete, rename and chmod are explicit
  authenticated operations; recursive deletion is not supported.
- Download and upload bodies are bounded by backend size limits and use normal
  token-authenticated localhost HTTP endpoints.
- Stored host credentials are loaded through the Vault flow. Plaintext
  credentials are not returned to the frontend by SFTP endpoints.
- SFTP subsystem rejection is stored as `unsupported`, not as an application
  crash or host failure.

### Process Lifecycle

- Tauri supervises the backend with a Windows Job Object and private stdin EOF. The full process and token boundaries are in [Security Rules](SECURITY_RULES.md).
- Backend exits when the parent process terminates.
- Tauri reports backend startup through `get_backend_status` as `starting`,
  `ready`, or `failed`; `ready` requires a successful authenticated
  `GET /health`, and token delivery failure terminates the sidecar instead of
  allowing an unauthenticated startup.
- Packaged data uses `%APPDATA%/com.netrix.app`; legacy `%APPDATA%/Netrix`
  entries are moved without overwriting destination conflicts.

## Known Limitations

- Quick-connect credentials use short-lived, one-time backend tickets created
  through authenticated HTTP before the WebSocket opens.
- Terminal command history and actual terminal output rows are not persisted in
  localStorage.
- Vault usage is optional for some user flows.
- Endpoint-level rate limits cover selected network tools and vault unlock.
- SFTP rename, delete, resumable transfers, and background transfer queues are
  not yet enabled; the current Files workflow supports browsing, text preview,
  bounded downloads, and bounded foreground uploads.

## Vault UX and Recovery

- Vault can be unlocked manually with a master password or via keychain-backed
  remembered password workflows.
- Vault reset remains an explicit destructive flow with required confirmation
  phrase (`RESET VAULT`).
- Master password change no longer requires a vault reset; existing secrets are
  preserved through authenticated key rotation.

## Hardening Priorities

1. Add CI security scans for Rust and npm dependencies.
2. Expand endpoint-level rate limits to remaining sensitive mutation endpoints.
3. Continue tightening inline-style CSP and desktop permissions before hardened
   releases.

## User Recommendations

- Enable full-disk encryption on the host OS.
- Prefer SSH keys over passwords.
- Keep Netrix and OS packages updated.
- Use strict host key policy in production environments.
